# Архітектура та внутрішня будова Бекенду aiCRM (Матеріали для БКР)

Цей документ створений для підготовки до презентації вашої Бакалаврської кваліфікаційної роботи (БКР). Він детально описує, як влаштований бекенд проєкту, які алгоритми та патерни проектування були використані, і як забезпечується цілісність даних.

---

## 1. Загальна архітектура: Модульний Моноліт (Modular Monolith)

Бекенд побудований на базі **Spring Boot** з використанням архітектурного стилю **Модульного Моноліту**. Замість того, щоб розбивати систему на окремі мікросервіси (що додало б непотрібної складності розгортанню), код розділений на логічні ізольовані домени (модулі).

### Основні модулі системи:
1. **`iam` (Identity & Access Management):** Відповідає за безпеку. Реалізує реєстрацію, авторизацію (JWT токени), OAuth2 інтеграцію (Google) та управління користувачами.
2. **`sales` (Продажі):** Ядро CRM. Управління угодами (Deals), клієнтами (Clients), завданнями (Tasks) та воронкою продажів (Kanban). Містить логіку фіксації історії угоди (Deal Events).
3. **`communications` (Комунікації):** Відповідає за омніканальність. Робота з Email, інтеграція з месенджерами (Telegram, Facebook), чат-сесії та внутрішні сповіщення (Notifications).
4. **`attachments` (Вкладення):** Модуль обробки файлів. Зберігає файли, взаємодіє з базою даних для трекінгу метаданих файлу.
5. **`search` (Семантичний пошук / RAG):** Взаємодіє з векторною базою даних (PgVector) для пошуку по змісту прикріплених документів.
6. **`ai` (Штучний Інтелект):** Оркестратор ШІ. Використовує Spring AI для підключення до LLM (Google Gemini, OpenAI, Mistral). Аналізує запити користувача та динамічно викликає функції CRM (Tool Calling / MCP).
7. **`shared`:** Спільні компоненти системи (глобальна обробка помилок `GlobalExceptionHandler`, конфігурації `PgVectorExtensionInitializer`, утиліти).

## 2. Ключові Алгоритми Системи

У проекті реалізовано кілька важливих та технічно складних алгоритмів, про які варто згадати на захисті:

### 2.1. Алгоритм RAG (Retrieval-Augmented Generation)
Використовується для того, щоб ШІ міг відповідати на питання по файлах, завантажених користувачем.
1. **Екстракція (Ingestion):** При завантаженні файлу запускається фоновий процес через RabbitMQ. Бібліотека `Apache Tika` "витягує" з файлу сирий текст.
2. **Чанкінг (Chunking):** Текст розбивається на менші фрагменти (чанки) за допомогою `TokenTextSplitter`. Це необхідно, щоб не перевищити ліміти контекстного вікна LLM.
3. **Векторизація (Embedding):** Кожен чанк відправляється до Embedding-моделі (напр., OpenAI або Google GenAI), яка перетворює текст у математичний вектор (масив чисел).
4. **Зберігання:** Вектори зберігаються в PostgreSQL з розширенням `pgvector`.
5. **Пошук (Retrieval):** Коли користувач щось питає, запит векторизується, і `PgVectorStore` знаходить найбільш схожі чанки тексту за метрикою відстані (`Cosine Distance`). Знайдений текст додається як контекст для LLM.

### 2.2. Алгоритм AI Orchestration (Динамічний виклик інструментів / MCP)
1. Користувач пише запит у чат.
2. `AiOrchestrator` збирає всі доступні інструменти (Tools) системи (наприклад, `SearchAITools`, `SalesAiFacade`).
3. Запит разом з метаданими інструментів відправляється в LLM.
4. LLM приймає рішення: замість текстової відповіді вона повертає JSON-запит на виконання конкретної функції.
5. `Spring AI` автоматично перехоплює цей запит, викликає відповідний Java-метод на вашому бекенді, отримує результат виконання бази даних і повертає його назад в LLM.
6. LLM генерує фінальну людську відповідь на основі отриманих даних.

### 2.3. Алгоритм асинхронної обробки (Message Broker)
Для важких операцій використовується RabbitMQ.
1. Коли завантажується файл, контролер одразу повертає відповідь "OK", а завдання кидається в чергу `file-processing-queue`.
2. `FileProcessingListener` забирає повідомлення, витягує текст і здійснює звернення до зовнішніх API у фоні, не блокуючи роботу основного потоку (HTTP-запиту).
3. Аналогічно працює `MessageOutboundListener` для розсилки повідомлень.

## 3. Патерни Проектування (Design Patterns)

На захисті комісія завжди любить питання про патерни. Ось які з них є у вашій системі:

1. **Facade (Фасад):**
   - *Де:* `SalesAiFacade`.
   - *Нащо:* Модуль ШІ не повинен знати деталі роботи бази даних продажів. Фасад об'єднує складні операції в простий інтерфейс, приховуючи внутрішні сервіси (`DealService`, `TaskService`) від інших доменів, підтримуючи слабку зв'язаність (Low Coupling).

2. **Observer / Listener (Спостерігач):**
   - *Де:* `FileProcessingListener`, `MessageOutboundListener`, Spring `@EventListener`.
   - *Нащо:* Для реакції на події без жорсткого зв'язування коду. Дозволяє реалізувати подієво-орієнтовану архітектуру (Event-Driven Architecture).

3. **Repository (Репозиторій):**
   - *Де:* Усі інтерфейси типу `DealRepository`, `NotificationRepository` (розширюють `JpaRepository`).
   - *Нащо:* Інкапсулює логіку роботи з базою даних, відділяючи SQL-запити від бізнес-логіки системи.

4. **Dependency Injection / Inversion of Control (Впровадження залежностей):**
   - *Де:* Всі конструктори класів (`@Service`, `@RestController`).
   - *Нащо:* Класи не створюють свої залежності самі через `new`, їх надає Spring Контейнер. Це робить код придатним до модульного тестування (можна підмінити залежності моками).

5. **Strategy (Стратегія):**
   - *Де:* Вибір моделей LLM у Spring AI (напр. підміна Google GenAI на OpenAI), або стратегії витягнення тексту `FileTextExtractor`.

## 4. Інваріанти на рівні Бази Даних (Data Integrity)

Чи використовувались інваріанти для шару бази даних? **Так, обов'язково!**
Це фундаментальна вимога для будь-якої надійної CRM системи. Інваріанти — це правила, які база даних не дозволить порушити за жодних умов.

1. **Ссылочна цілісність (Foreign Keys Constraints):**
   - Всі сутності пов'язані через зовнішні ключі (`@ManyToOne`, `@OneToMany`). Наприклад, `DealEvent` не може існувати без існуючого `Deal`. База даних видасть помилку (Constraint Violation), якщо спробувати додати подію до неіснуючої угоди.
2. **Унікальність (Unique Constraints):**
   - Email користувача завжди унікальний (`@Column(unique = true)`). БД не дозволить зареєструвати двох користувачів з одним email, навіть якщо два HTTP-запити прийдуть одночасно.
3. **Обмеження Not Null:**
   - Обов'язкові поля в БД позначені як `nullable = false` (напр., назва угоди). Спроба зберегти об'єкт без імені призведе до відмови запису (`DataIntegrityViolationException`).
4. **Контроль станів (Enums у БД):**
   - Стан угоди (`DealStage`), статус завдання (`TaskStatus`) мапляться на `VARCHAR` або PostgreSQL типи Enum. Записати в це поле випадковий рядок "hello" неможливо.
5. **Транзакційність (ACID інваріанти):**
   - Використання анотації `@Transactional` над сервісними методами. Якщо під час складного процесу (наприклад, додавання угоди + додавання DealEvent) сталася помилка на останньому кроці, база даних **відкотить (Rollback)** усі попередні зміни. Система ніколи не опиниться в "напівготовому" стані.

## 5. Функціональні можливості Фронтенду та Клієнт-Серверна Інтеграція

Хоча основна бізнес-логіка зосереджена на бекенді, інтерфейс користувача (Frontend) є критично важливою частиною системи, що забезпечує безпосередню взаємодію з користувачем. Він реалізований на базі сучасного фреймворку **Next.js (React)** та адаптований під преміальний UX/UI.

### 5.1. Ключові функції Фронтенду:
1. **Адаптивний мобільний інтерфейс (Mobile Responsiveness):**
   - Система повністю підтримує мобільні пристрої. Статична бічна панель (Sidebar) на екранах смартфонів трансформується у висувне оверлей-меню (Sidebar Drawer), кероване через глобальний стейт `zustand`.
   - Всі інформаційні таблиці (клієнти, угоди) обгорнуті в адаптивні контейнери, що дозволяють горизонтальну прокрутку без руйнування загального макету.
   - Вікна детального перегляду угод та поштові розділи автоматично перемикаються у повноекранний режим з навігацією кнопкою "Назад" на мобільних пристроях.

2. **Завантаження файлів та управління вкладеннями (File Attachments System):**
   - **Інтерактивне прикріплення файлів:** У картках завдань на Kanban-дошці та в панелі деталей угоди інтегровано інструменти для завантаження файлів (PDF, DOCX, TXT, зображення тощо) за допомогою стандартного `multipart/form-data` API.
   - **Зворотний зв'язок у реальному часі:** Візуалізація статусу завантаження файлу, відображення списку вже прикріплених файлів з метаданими (ім'я файлу, розмір, дата завантаження).
   - **Інтеграція з ШІ (RAG):** Завантажені текстові документи автоматично стають контекстом для вбудованого ШІ-асистента.

3. **Глобальний ШІ-Асистент (Global AI Sidepanel):**
   - Висувна бічна панель, яка відкривається на будь-якій сторінці CRM. Користувач може обрати конкретного ШІ-провайдера (Google Gemini, OpenAI GPT, Mistral або Groq) через спадне меню.
   - Підтримка контекстного аналізу чатів: в один клік користувач може передати історію листування з клієнтом у ШІ для генерації сумаризації або пропозицій.

4. **Омніканальний комунікаційний хаб (Real-time Messaging & Mailing):**
   - **Messenger:** Повноцінний інтерфейс чату у реальному часі, підключений до Spring Boot WebSocket-сервера. Дозволяє миттєво відповідати клієнтам у Facebook Messenger, перейменовувати діалоги для зручності та видаляти застарілі сесії.
   - **Mailing Client:** Інтерфейс електронної пошти з підтримкою вхідних/вихідних листів та можливістю планування відкладеної відправки (Scheduled Emails) за часом.

5. **Інтерактивна Kanban-дошка:**
   - Реалізована за допомогою `@dnd-kit` бібліотеки, що дозволяє користувачу перетягувати (Drag-and-Drop) завдання між колонками "Planned" (Планується), "In Work" (В роботі) та "Done" (Виконано).
   - При переміщенні завдання у стовпчик "Done", фронтенд динамічно відкриває діалогове вікно для фіксації результату виконання задачі.

6. **Багатомовність (i18n):**
   - Повний переклад інтерфейсу на дві мови: Українська (за замовчуванням) та Англійська. Зміна мови відбувається миттєво без перезавантаження сторінки завдяки реактивному сховищу конфігурацій.

### 5.2. Технологічний стек Фронтенду:
* **Framework:** Next.js (React, App Router)
* **Styling & Layout:** Tailwind CSS + Vanilla CSS (мобільна адаптивність, скляний ефект Glassmorphism, темна тема Dark Mode)
* **State Management:** Zustand (управління станом мобільного меню, ШІ-панелі та мовними локалізаціями)
* **Client-Server Sync:** React Query (TanStack Query) + Axios (для оптимістичних оновлень даних без перезапитів до API)
* **Real-time Communication:** Native WebSockets Client (для чатів та сповіщень)
* **Icons & UI Elements:** Lucide React + Radix UI primitives (доступність та відповідність стандартам WAI-ARIA)
