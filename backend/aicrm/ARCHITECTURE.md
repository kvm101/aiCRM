# aiCRM Backend Architecture

## Overview
Додаток **aiCRM** використовує архітектуру **Модульного моноліту (Modular Monolith)**, що базується на принципах **Domain-Driven Design (DDD)**. 
Замість класичної шарової архітектури, де всі контролери та сервіси лежать в одній купі, код розділено на незалежні бізнес-домени. Це забезпечує високу зв'язність (high cohesion) всередині модулів, зменшує залежності між ними (loose coupling) та дозволяє легко масштабувати чи виносити модулі в окремі мікросервіси в майбутньому.

## Функціональні вимоги (Functional Requirements)
- **Управління користувачами (IAM)**: Реєстрація, автентифікація, управління сесіями (за допомогою `HttpOnly` cookie `user_id`), перегляд та редагування профілів.
- **Управління клієнтами (Sales)**: Ведення бази клієнтів — створення, перегляд, фільтрація, оновлення (PATCH) та видалення клієнтських записів (CRUD).
- **Управління завданнями (Sales)**: Планування роботи. Створення завдань, прив'язка до користувачів, зміна статусів (`PLANNED`, `IN_WORK`, `DONE`), робота з дедлайнами та тегами.
- **Комунікації (Communications)**: Відправка електронних листів, інтеграція з месенджерами (Telegram вебхуки) та асинхронна обробка повідомлень через RabbitMQ. Зберігання історії чатів та повідомлень.

## Нефункціональні вимоги (Non-Functional Requirements)
- **Архітектура**: Modular Monolith, Domain-Driven Design (DDD).
- **Безпека**: Авторизація реалізована за допомогою безпечних `HttpOnly` cookies, що унеможливлює XSS атаки на сесію.
- **Масштабованість**: Можливість легкого виділення будь-якого модуля (`iam`, `sales`, `communications`) в окремий мікросервіс завдяки слабкій зв'язності (loose coupling).
- **База даних**: Реляційна СКБД з використанням Spring Data JPA / Hibernate для ORM. Всі операції, що змінюють стан БД, ізольовано транзакціями.
- **Обробка помилок**: Використання єдиного механізму обробки винятків (`GlobalExceptionHandler`), що забезпечує стабільний формат відповідей для клієнта (навіть при помилці 500).

## Структура Проєкту
Вихідний код знаходиться у `src/main/java/vasyl/karpliak/aiCRM/` і поділений на такі основні домени:

### 1. `iam` (Identity and Access Management)
Відповідає за користувачів системи, автентифікацію, авторизацію та ролі.
- **`controller`**: `AuthController`, `UserController`
- **`service`**: `UserService`
- **`repository`**: `UserRepository`
- **`domain`**: `User`
- **`dto`**: `LoginDTO`, `RegistrationDTO`, `UserDTO`
- **`enums`**: `UserRoles`

### 2. `sales` (Sales & CRM Core)
Ключовий модуль CRM для управління клієнтами та завданнями, пов'язаними з ними.
- **`controller`**: `ClientController`, `TaskController`
- **`service`**: `ClientService`, `TaskService`
- **`repository`**: `ClientRepository`, `TaskRepository`
- **`domain`**: `Client`, `Task`
- **`dto`**: `ClientDTO`, `TaskDTO`
- **`enums`**: `ClientStatus`, `TaskStatus`

### 3. `communications`
Модуль для роботи з повідомленнями та зовнішніми каналами зв'язку (Email, Telegram).
- **`controller`**: `MailController`, `TelegramWebhookController`
- **`service`**: `MailService`
- **`adapter`**: Інтеграція із зовнішніми каналами (`TelegramAdapter`, `ChannelAdapter`).
- **`config`**: Налаштування інфраструктури (`RabbitMQConfig` для асинхронної обробки повідомлень).
- **`repository`**: `MessageRepository`, `ChatSessionRepository`
- **`domain`**: `MailData`, `Message`, `ChatSession`, `Bot`
- **`dto`**: `UnifiedMessage` (для уніфікації повідомлень з різних каналів)

### 4. `shared`
Спільне ядро системи (Shared Kernel). Містить глобальні налаштування та обробники помилок.
- **`controller`**: `HealthController`, `GlobalExceptionHandler`

## Архітектура всередині доменів (Package by Component)
Кожен домен ізольований і має власну внутрішню структуру шарів:
- **`controller`**: REST API шар. Приймає HTTP-запити, валідує вхідні дані та повертає відповіді.
- **`service`**: Шар бізнес-логіки. Містить ключові бізнес-правила та керує транзакціями (`@Transactional`).
- **`repository`**: Шар доступу до даних. Spring Data JPA інтерфейси для роботи з базою даних.
- **`domain`**: JPA Сутності (`@Entity`), що відповідають за структуру таблиць БД.
- **`dto`**: Об'єкти передачі даних (Data Transfer Objects), що інкапсулюють дані, які відправляються чи приймаються через API.
- **`enums`**: Перелічення для фіксованих станів (статуси, ролі).
- **`adapter`**: Адаптери для взаємодії із зовнішніми системами та API.
- **`config`**: Конфігураційні класи для налаштування інфраструктури (RabbitMQ тощо) в межах модуля.

## API Ендпоінти (Endpoints)

### 🔐 Авторизація та Користувачі (`/auth`, `/users`)
- `POST /auth/register` — Реєстрація нового користувача у системі.
- `POST /auth/login` — Авторизація користувача. Повертає HttpOnly cookie `user_id`.
- `GET /users/{id}` — Отримати деталі користувача за його ID.
- `GET /users/filtered` — Отримати список користувачів (з підтримкою фільтрації).
- `PUT /users/{id}` — Повністю оновити профіль користувача.
- `DELETE /users/{id}` — Видалити користувача з системи.

### 👥 Клієнти (`/clients`)
- `POST /clients` — Створити нового клієнта.
- `GET /clients/filtered` — Отримати список клієнтів (з можливістю фільтрації).
- `GET /clients/{id}` — Отримати детальну інформацію про конкретного клієнта.
- `PATCH /clients/{id}` — Часткове оновлення інформації про клієнта (тільки змінені поля).
- `DELETE /clients/{id}` — Видалити клієнта з бази.

### 📋 Завдання (`/tasks`)
- `POST /tasks` — Створити нове завдання для працівника.
- `GET /tasks` — Отримати список усіх завдань.
- `GET /tasks/filtered` — Отримати список завдань із застосуванням фільтрів.
- `GET /tasks/{id}` — Отримати деталі конкретного завдання за ID.
- `PUT /tasks/{id}` — Оновити всю інформацію про завдання.
- `DELETE /tasks/{id}` — Видалити завдання.

### ✉️ Комунікації (`/mail`, `/webhooks`)
- `POST /mail/mail` — Надіслати електронний лист.
- `POST /webhooks/telegram/{teamId}` — Обробка вхідних вебхуків від Telegram та їх передача до RabbitMQ.

### ⚙️ Спільні
- `GET /health` — Перевірка статусу працездатності додатка (Health Check).
